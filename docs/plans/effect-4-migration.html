Effect 4.

Upgrade the runtime.
Preserve the app’s behavior.

Amical already uses Effect for desktop services, dictation, synchronization, and telemetry. The migration is bounded in package scope, but several paths depend on precise Effect 3 runtime behavior.

Recommendation

Pin Effect 4.0.0-rc.115, move the desktop compiler to TypeScript 5.9.3, and migrate in one coordinated branch. First prove immediate fiber startup, error settlement, and scope cleanup against the exact RC. Then migrate the wider service graph and package the app.

Prefer a clean Effect 4 design where the old approach no longer fits. Internal adapters and v3 workarounds may be rewritten. Surface the recommendation, tradeoffs, and behavior changes before implementing a substantial rewrite. See 3.7 Rewrite decisions.

Follow-up review: three migration regressions fixed
  • FIFO lock handoff: v4 resumes Deferred waiters synchronously. A queued chunk could start before the preceding failure retired its session; a long synchronous queue could also overflow the stack. Completing the ticket with Effect.yieldNow schedules its continuation while retaining ownership and cancellation safety. Tests cover two chunks, interruption after handoff, and 2,000 queued users.

Lifecycle V2 receives no additional changes from this fix.

3.3 Immediate-start behavior — observed in isolated RC probes

runFork, runForkWith, runPromise, and runPromiseWith executed the synchronous prefix before returning in rc.115. Root runner options have no startImmediately field.

Child and detached fork combinators defer startup by default. Their { startImmediately: true } option restores immediate startup where the app requires it. Review main/lifecycle/effect/session-work.ts:233 in particular.

Effect.forever now yields between iterations. The activity schedule keeps its explicit 301–360 second or one-hour sleep and uses { disableYield: true } to register the next timer without another scheduler handoff. Sleep still suspends the fiber for the intended interval. 

// Static telemetry bridge; covered by the custom tracer tests.
const context = Context.make(Tracer.Tracer, tracer);
export const runFork = Effect.runForkWith(context);
export const runPromise = Effect.runPromiseWith(context);
export const runPromiseExit = Effect.runPromiseExitWith(context);

The isolated probe confirmed immediate startup and tracer invocation for this context pattern. It did not migrate or validate the full app. Runtime guide · Forking guide

3.4 Error handling is the first semantic gate

Observed RC difference

A failure with both a typed error and a finalizer defect retains both in its raw Exit. In rc.115, Effect.catch can recover the typed error and discard the defect; Effect.result, Effect.mapError, Effect.orDie, and typed matching can also hide it. The conversion uses catchCause plus Cause.map to transform typed errors while retaining the complete cause. Regression tests cover auth, cloud fallback, remote config, and finalizer defects.

Review catchAll → catch, catchAllCause → catchCause, catchAllDefect → catchDefect, and test either → result changes together. Audit existing catchTags and error taps where finalizers can also fail. Keep application-level defect reporting through cause-aware handling at the relevant boundaries. Pinned recovery implementation

3.5 Cause representation and test changes

V4 uses a flat collection of reasons. Replace Cause.failureOption with findErrorOption; dieOption becomes findDefect, which returns a Result, not an Option. Read defect values from cause.reasons using Cause.isDieReason. sequential becomes combine, which deduplicates equal reasons while preserving first-occurrence order; interruption checks become hasInterrupts / hasInterruptsOnly. Exit.isInterrupted becomes Exit.hasInterrupts in settings sync and its tests.

The RC has no Cause.electFailures export. Update probes that describe v3 mechanics to describe actual v4 behavior. Keep tests for the app’s typed-error priority, original error identity, null rejection handling, and exactly-once defect capture.

Cause.originalError is also removed. Isolated probes preserved raw defect identity through plain, single-span, and nested-span failures. Use the raw defect value for deduplication in the live session and retain tests for those cases. Cause source

Start in types/errors/settle.ts, services/transcription/live-transcription-session.ts, services/auth-retry.ts, and tests/effect/error-model-probes.test.ts. Cause migration guide

3.7 Rewrite decisions

Updated direction: prefer a durable v4 implementation where the old design no longer fits. These recommendations distinguish confirmed library changes from optional architecture changes.

Area Recommendation Reason and decision gate
Runtime / tracer bridge
Rewrite now 		Replace the old runtime-building shell with context-based runners and the v4 tracer interface. The old Runtime type and tracer-layer construction APIs are gone. Remove obsolete initialization machinery. Direct context runners fit the current static tracer. A fresh RC probe also showed that a cold ManagedRuntime starts immediately for a synchronous layer; do not carry forward the v3 assumption that it always defers startup. Runtime guide · ManagedRuntime source
Error settlement / recovery
Rewrite now 		Rewrite cause inspection and recovery at affected boundaries around v4 reasons and raw defect identity. Mixed-cause behavior changed. Make error priority and defect reporting explicit where needed; remove old proxy normalization and revise v3-only probes. Verify null failures, interrupted finalizers, and exactly-once reports. See 3.4–3.5.
Custom FIFO token lock
Retain for ordering 		Keep the explicit FIFO handoff. Complete each waiter with Effect.yieldNow to schedule its continuation; v4's synchronous Deferred wakeup otherwise changes failure ordering and can recurse through a long queue. An rc.115 probe showed a new semaphore acquirer overtaking an already queued waiter. Native Semaphore(1) does not satisfy the current FIFO contract. Removing this lock would require a resource-serialization design, such as ordered jobs with one worker. Include VAD reset, final flush, and history retry as well as streaming chunks: they share these locks. That rewrite is an option to compare, not a demonstrated simplification. Semaphore implementation
Boot scope ownership
Design review 		Evaluate an outer crash-reporting scope with ordinary scoped acquisition for the inner application graph. This is an architecture option, not a new v4 requirement. Keeping telemetry alive is insufficient: inner rollback can block initialization from rejecting, so the current crash reporter never runs. Compare reporting before rollback, a defined bounded rollback policy, and current ownership. Test blocked cleanup and a pending sibling initializer before recommending a rewrite; see 4.1.
Session fiber ownership
Evaluate primitives 		Evaluate FiberSet for generic running-fiber bookkeeping and native scopes for background workers. Keep cloud/provider ManagedRuntime ownership. Production closes chunk admission before draining (transcription-service.ts:912,962), so FiberSet.awaitEmpty may meet the real requirement: drain accepted work and let abort release the wait. Snapshot semantics and SessionWork.settled() are currently test/API details, not proven product constraints. Verify the chosen drain and retain explicit error settlement. FiberMap holds one fiber per key and would replace earlier work under the same session key; it cannot replace the whole lifecycle registry directly. Delivery and surviving obligations need distinct lifetimes. FiberSet source · FiberMap source
Electron quit boundary
Design review 		Require asynchronous finalizer completion before normal application exit; evaluate a guarded quit sequence if needed. This is a pre-existing integration risk. The only quit hook (main/app.ts:157) returns the cleanup Promise without preventing termination. A successful exit can therefore hide incomplete cleanup. Decide repeated-quit, cleanup-error, and timeout behavior, and prove completion in a packaged app. Electron quit semantics

For each non-clean migration, report the old design, supported v4 alternative, recommended rewrite, behavior changes, and effort/test impact before implementation. Service-tag renames and retained queue operations can follow the guide directly. Any compatibility wrapper needs a concrete reason to survive the migration.

4Behavior contracts

These are the current behavior checks. Separate product requirements from tests that pin a v3 implementation detail. Update the latter for the chosen v4 design; document any proposed product-behavior change before implementation.

4.1

Startup failures reach crash reporting before cleanup can block

Preserve the original boot error, telemetry flush, and fatal dialog even when a sibling’s cleanup is pending. Register release before fallible initialization; own and await or cancel pending initialization when a sibling fails. The chosen scope design must clean up resources once in dependency order.

The essential requirement is usable crash reporting and reliable cleanup. Keeping the entire partial graph alive is the current solution; the scope review in 3.7 may propose a smaller retained graph and explicitly revised cleanup expectations.

Evidence: main/runtime/app-runtime.ts:1, main/runtime/layer-helpers.ts:16. Gate: existing tests/main/app-layers.test.ts failure and shutdown cases, extended with a pending initializer and a blocked finalizer. The existing late-failure case does not prove those scenarios. Pinned layer cleanup

4.2

The first dictation fork starts immediately

The synchronous prefix must run before the runner returns, including on the first call. The lifecycle code uses this to register work and telemetry obligations without a scheduling gap.

Evidence: main/runtime/telemetry-runtime.ts:6. Gate: keep the first test in tests/main/telemetry-runtime.test.ts:15; extend coverage to Promise/exit runners and callback-created work where needed.

4.3

Errors retain identity and defects stay visible

Promise boundaries reject with the same typed error value. In a mixed cause, settlement preserves the app’s failure priority and reports each dropped defect exactly once. Pure cancellation does not become a domain failure or a bug report.

Evidence: types/errors/settle.ts:3, services/transcription/live-transcription-session.ts:52. Gate: error-model probes, settlement tests, and live-session defect-capture tests.

4.4

Token acquisition remains FIFO and cancellation-safe

Waiters enter in arrival order. An interrupted waiter is removed; handoff cannot lose the token; release happens once. Keep the custom lock until an alternative proves all of these properties.

Evidence: services/transcription/token-lock.ts:5. Gate: tests/services/token-lock.test.ts, including interrupted handoff and mixed Promise/Effect use.

4.5

Identity changes fence old work

Logout and account switches cancel or retire old requests before new-account work can commit. Settings sync and activity reporting retain their single-flight, debounce, retry, and shutdown rules. Auth refresh remains shared by concurrent callers.

Gate: settings-sync service/client, activity-reporting service/client, auth-refresh and auth-retry suites. Add targeted RC cases for queued work during scope close only where coverage is missing.

4.6

Telemetry completes once; quit completes without a forced kill

Nested spans keep parentage; separate sessions keep distinct trace IDs. A throwing telemetry sink cannot fail dictation. Cancellation, finalization, and provider disposal leave no stuck background work when the app quits. Observe finalizer completion before process exit; an exit code alone is insufficient. Test repeated quit requests and the chosen error/timeout policy.

Gate: telemetry runtime/trace tests, lifecycle session-work tests, cloud provider tests, and an explicit packaged clean-exit check. The current E2E close helper can kill a hung app, so it is insufficient evidence by itself.

  • The full application suite and typechecks ran on v4, with local macOS arm64 packaging, native smoke checks, and packaged E2E. Windows x64/arm64 and macOS x64 were not validated locally, and no remote CI run was started.
  • Live microphone dictation and graceful quit under real active provider work were not manually exercised. Native whisper binaries were smoke-tested without rebuilding the user's separately modified whisper source.

7Release & rollback

7.1 Release criteria

  • Exact RC/compiler pins and reviewed lockfile.
  • All six behavior contracts pass with no unresolved new failures.
  • Full unit suite runs in CI; packaged checks pass for release targets.
  • Internal sessions show no new dropped dictation, duplicate telemetry, wrong-account writes, or stuck quit.
  • Compare startup, stop-to-paste latency, and memory after repeated sessions with the v3 baseline. Investigate sustained regressions before promotion.

7.2 Rollback unit

Keep the dependency update, API migration, and corresponding tests as one revertible release unit. If a regression appears, pause promotion and use a corrective build from the known-good v3 code and lockfile.

Validate the updater’s version rules before choosing an older artifact directly. The plan makes no data-format or cloud-protocol changes, so rollback should not require a database downgrade.
